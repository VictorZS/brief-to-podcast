# 把报错变成下一步：中文简报入门的一次走查

日期：2026-11-13。观察期间：11/9—11/11。案例版本：[`132cdbc`](https://github.com/VictorZS/brief-to-podcast/commit/132cdbcc5595c225f2feba55bc837d557fe1a77b)。状态：**方法候选**；本文依据 AI 代理走查与工程检查整理，尚无外部使用者观察。

这周关注的生活场景是：把已有文字准备成一份早餐或通勤时能听的简报。这是待验证的需求假设。工具已经能生成音频，但使用者仍要整理输入、处理报错、检查内容，再判断是否值得收听。

本轮补齐的是其中一段：**将输入要求、具体报错、修正命令和再次确认结果的步骤放在一起。** 这条路径已被代理实际跑通；普通使用者是否因此更省力，还需要观察。

## 原来的负担，具体落在哪一步

原有输入契约说明了字段与校验规则，也提供了完整英文样例。准备中文材料时，使用者仍需自己把这些规则组织成操作：哪些内容一起改、计数怎样更新、报错之后先检查哪里。这里描述的是文档要求，尚未测量真人的准备时间或求助次数。

以修改口播为例：最终稿变了，记录中的字符数也要同步。否则引擎会拒绝继续生成。这项检查有作用；值得改善的是发现不一致之后的修正路径。

| 环节 | 原有支持 | 本轮补充 | 还不能下的结论 |
|---|---|---|---|
| 准备输入 | 完整英文样例与字段说明 | 中文单事实样例、对应初稿及字段关系表 | 小样例更短，不等于同样任务完成得更快 |
| 修改后报错 | 提示字符数与实际口播不符，契约给出计算表达式 | 可执行的复算命令，随后重新渲染 | 代理能修复，不等于新手能独立修复 |
| 判断是否完成 | README 列出结果状态 | 明确读取 `audio_status`，核对文件，再阅读和试听 | 技术检查通过，不等于听感或内容质量合格 |

这些变更见 [PR #2](https://github.com/VictorZS/brief-to-podcast/pull/2) 和对应版本的[中文指南](https://github.com/VictorZS/brief-to-podcast/blob/132cdbcc5595c225f2feba55bc837d557fe1a77b/docs/getting-started.zh.md)。输入契约与默认检查保持不变。

## 实际跑通了什么

11 月 11 日的走查刻意在样例口播中增加一句话，保留旧计数。渲染返回错误 `compression.after_chars does not match the actual script`；执行指南中的复算命令后，文本渲染成功。这个构造案例验证了修正步骤可执行，不能说明真实用户多常遇到该错误。

走查还暴露了环境条件：首次命令实际调用 Python 3.9.6，低于文档要求，音频读取失败。确认使用 Python 3.14.5 后，指南全部五个 shell 代码块在隔离目录中执行完成；Tingting 生成了 **38.653 秒长**的中文音频，五个输出文件的哈希核对一致。这些是 [PR #2 中记录的本地运行结果](https://github.com/VictorZS/brief-to-podcast/pull/2)，没有独立真人试听。环境改变后的成功不能全部归因于指南。

这里的 38.653 秒是音频长度，不是完成任务的时间。阅读材料、准备输入、首次安装、校对和试听的真人耗时均未测量。

已有 28 项自动测试通过，[合并后的 CI](https://github.com/VictorZS/brief-to-podcast/actions/runs/43014229040) 也检查了英文与中文文本样例。CI 没有验证 Mac 上的音频或真实使用体验；音频依据来自上述本地走查。

## 为什么先补指南

这轮选择了能单独检查的小改动：提供一个中文例子，把失败后的操作写完整。暂时没有加入自动写稿、普通文本转换或新界面。当前还不知道哪一步最妨碍真实使用，大范围重做会同时改变太多条件，难以判断改进来自哪里。

这个选择也有明确局限。更多说明仍然需要人读，JSON 仍要编辑；不熟悉命令行的人可能在第一步就停下。音频还需要 Mac、合适版本的 Python 和已安装语音；来源需要有效 HTTPS 链接。示例不依赖付费 AI 账户，但设备、学习和维护的投入没有测量，不能据此宣称使用成本很低。

中文样例同时改变了语言和内容复杂度，同一代理也已经熟悉契约。因此，这次没有形成无偏的前后效率对照。如果指南让人多读了一篇说明，却仍无法自己修正输入，就应考虑更直接的编辑或检查入口。

## 值得继续检验的方法

对需要准备结构化输入的工具，可以把已知失败整理成一条完整路径：**看见具体错误 → 找到需要修改的内容 → 执行修正 → 确认本次结果**。本例中，指南补齐了原来需要自行组合的操作；它是否减少理解与求助负担，是下一步要检验的机制。

11/9 的英文例子与 11/11 的中文例子都能复现字符数校验，但两次都是构造的代理测试。它们没有证明方法已在不同人群中有效，因此仍保持“方法候选”。这也与[上一篇发布验收复盘](2026-11-08-release-verification.md)不同：本篇讨论使用过程中的恢复步骤，前篇讨论版本发布后的检查范围。

下一次只追一个问题：**自愿参与者能否在不被代跑的情况下，依照指南完成一次输入修改与错误恢复？** 先用虚构素材，记录自述技术熟悉度、卡点与求助；首次设置和之后的准备、检查、纠错分别记录。熟悉工具与不熟悉工具的观察分开。若主要障碍是安装，或修复后仍看不到收听价值，就调整优先项。

截至本篇整理时，真实激活、跨周复用、不熟悉工具者的体验观察，以及完整任务的时间与费用仍为未知。欢迎通过[使用反馈](https://github.com/VictorZS/brief-to-podcast/issues/new?template=usage_feedback.yml)描述具体卡点，无需公开私人材料。

**English takeaway:** Connect an input requirement to a concrete error, a repair step, and a fresh completion check. The Chinese guide was executed by an agent; this establishes a reproducible recovery path, not easier onboarding for real users. Setup, preparation, correction, and continued use still need observation.
